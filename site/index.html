The line

Six stations, in order. You can't skip ahead: the engine checks each station's output before the next one starts.

  1. 1

    Interview

    The interviewer

    One simple question at a time, never "which framework?". It raises the strongest objection to your idea and asks for your answer, then writes numbered requirements and success criteria you can measure, and waits for your yes.

    01-brief.md

  2. 2

    Research

    Four researchers in parallel

    Competitors, real complaints, trends, open niches, GitHub repositories. Every fact needs a link and a word-for-word quote. The engine loads the page and looks for it; one invented quote and the whole batch is redone.

    02-research.md · 02-sources.json

  3. 3

    Hooks

    The hook writer

    Opening lines, in-product copy and a launch post for your one main platform. Numbers need a source. A detector rejects the phrases that make readers scroll past AI copy.

    03-hooks.md

  4. 4

    Screenplay

    The screenwriter

    The build written like a film. Every requirement gets a machine check, and every check is run on the empty project first: one that already passes proves nothing and goes back. A few checks are sealed where the builders can't see them.

    04-screenplay.md · 04-acceptance.json

  5. 5

    Arena

    3 managers, 3 developers, 3 designers, 1 auditor

    Each team builds in its own copy of your project. The engine judges every commit in a clean room, rivals cross-examine, and an auditor scores what's left before reading anyone's claims.

    scoreboard.md · graveyard.md

  6. 6

    Ship

    The release crew

    The winner is merged and re-checked. You get a README written for someone who has never opened a terminal, a launch kit, a report and a dashboard.

    README.md · LAUNCH.md · REPORT.md

Three managers. One rule.

Lose honestly and your branch is kept. Lie once and your team is gone: the copy of the project, the branch, every line of work. The lie stays in the graveyard with the output that disproved it.

SprintThe smallest product that fully works, shipped first.
FortressNothing breaks: tests, edge cases, security, accessibility.
SparkThe boldest experience people remember.

  1. Evidence or silence. Every "done" comes with a check the engine runs. "Not verified" is always allowed.

  2. A claim that fails its own check is a lie. The team is deleted on the spot.

  3. Tests are untouchable. A commit that changes a protected file is tampering. Same fate.

  4. Accuse only with proof. If the engine can't reproduce the defect you reported, you are the one deleted.

  5. Hidden checks stay hidden. They run only at the official verification, so building to the visible tests shows on the scoreboard.

  6. The judge checks your commit, not your desk. Every verdict runs in a fresh copy of what you committed, outside your project.

Why you can trust the result

Checks that can fail

Every requirement is traced to a check, and every check is run before any code exists. A check that passes on an empty project is rejected, because it proves nothing.

A signed ledger

Approvals, verdicts, deaths and the crown are written to a hash chain signed with a key kept outside your project. Edit a verdict by hand and scoring refuses it.

A safety scan

Every verified commit is scanned for committed secrets and for dependencies that don't exist. A team with either can't be crowned.

Questions

Does it really delete a team's work?

Yes. The team's git worktree and branch are removed, and the team name can never be used again in that project. What stays is the dossier: the claim, the check and the output that disproved it.

What if a check fails for a silly reason?

Managers run a private precheck first; it runs the same visible checks and kills nobody. A timeout or a refused command counts as "unproven", not as a lie. Only a check that ran and contradicted the claim kills.

Can the builders see the hidden checks?

No. They are sealed into a private folder outside your project before the arena opens, hooks stop agents from reading it, and only titles and pass or fail reach the teams. It keeps honest agents honest; it is not a sandbox against someone with access to your machine.

Where does my project go?

Nowhere. Skillsmith has no server. Everything lives in your folder, in .skillsmith/, under git, plus a private folder in your home directory. The researchers use the web tools your Claude Code already has.

Which languages does it speak?

Skillsmith is written in English and produces English files. You can write to it in another language and Claude will answer in it; if your product itself should be in another language, say so in the interview.

Does it work outside Claude Code?

The plugin has no bin/ folder, so Claude Cowork can install it. The skills use the open Agent Skills format; the arena needs subagents and a shell, so other tools may run only parts of it.
